# WCAG 2.1 AA Mapping Matrix

**Project:** Gqeberha Community Clinic — Accessible Healthcare Booking Portal

This matrix maps WCAG 2.1 accessibility criteria to the static HTML/CSS wireframes in `/wireframes` and the planned React single-page application in `/src`. The implementation and verification status must be updated as development and testing progress.

## WCAG 2.1 AA Criteria

| # | Criterion ID and name                                              | Target interface component                                                       | Technical implementation                                                                                                                                                                                                                                                                                                                          | Verification strategy                                                                                                                                                                                                                         |
| - | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **1.3.1 Info and Relationships (A)**                               | Booking form, urgency radio group, service directory and page structure          | Use semantic HTML landmarks and correctly nested headings. Associate every form control with a `<label>`. Group urgency radio buttons in `<fieldset>` with a `<legend>`. Associate instructions with controls using `aria-describedby`. Render directory results as a semantic list where appropriate.                                            | **Automated:** Run axe-core to identify label and landmark issues. **Manual:** Inspect the accessibility tree and use NVDA to confirm that headings, form labels, hints and radio-group legends are announced correctly.                      |
| 2 | **1.4.3 Contrast (Minimum) (AA)**                                  | Body text, links, buttons, hints and error messages                              | Use the audited colour combinations documented in `main.css`. The documented minimum text contrast is 7.40:1 for muted text on the sage background, exceeding the 4.5:1 requirement for normal text. Large text requires at least 3:1.                                                                                                            | **Computed:** Record contrast ratios using the WCAG relative-luminance formula. **Automated:** Test rendered pages with axe-core or Lighthouse. **Manual:** Verify text, hover, focus and error states using a contrast checker.              |
| 3 | **1.4.4 Resize Text (AA)**                                         | All wireframes and React views                                                   | Use scalable text and responsive layouts. Avoid fixed-height containers that clip content. Allow text, buttons, form controls and navigation to wrap or reflow when enlarged.                                                                                                                                                                     | **Manual:** Increase browser text size to 200% and confirm content and functionality remain available without clipping or overlap. Check responsive layouts at narrow viewport widths.                                                        |
| 4 | **2.1.1 Keyboard (A) and 2.1.2 No Keyboard Trap (A)**              | Navigation, directory filters, booking form and React interactions               | Use native links, buttons, inputs, selects and radio buttons wherever possible. Ensure custom React controls support keyboard interaction and expose their state. If a modal is implemented, manage focus appropriately and provide a reliable way to close it.                                                                                   | **Automated:** Add React Testing Library tests for keyboard interaction and custom control states. **Manual:** Navigate the entire application using only the keyboard and verify that focus is never trapped unexpectedly.                   |
| 5 | **2.4.1 Bypass Blocks (A)**                                        | Repeated header and navigation                                                   | Place a visible-on-focus "Skip to main content" link before the repeated navigation. Give the main content a matching target ID, such as `id="main"`. In the React application, manage focus after view changes where needed.                                                                                                                     | **Manual:** Load each page, use Tab to reach the skip link, activate it and verify that the main content is reached. Check that landmarks are exposed correctly.                                                                              |
| 6 | **2.4.7 Focus Visible (AA)**                                       | Links, buttons, inputs, selects, radio buttons and other interactive controls    | Provide a clear `:focus-visible` indicator. The shared stylesheet documents a blue focus colour (`#2B6CB0`) with a contrasting outline and offset. On dark backgrounds, use a suitable contrasting indicator, such as the documented yellow (`#FFD54F`). Do not remove the browser's focus indication without providing an effective replacement. | **Manual:** Tab through all pages and states. Verify that each interactive element has a clearly visible focus indicator against its actual background. Check contrast for the focus indicator.                                               |
| 7 | **3.3.1 Error Identification (A) and 3.3.3 Error Suggestion (AA)** | Booking form and React form validation                                           | Use native HTML constraints in the static wireframe. In React, identify invalid fields with clear text messages, set `aria-invalid="true"` when appropriate, and associate each error message with its field using `aria-describedby`. Where possible, explain how to correct the error.                                                          | **Automated:** Test required fields, invalid email formats, error associations and validation states. **Manual:** Use keyboard navigation and NVDA to confirm errors are identifiable, understandable and associated with the correct fields. |
| 8 | **4.1.3 Status Messages (AA)**                                     | React directory result counts, availability updates and form submission feedback | In the React application, use an appropriate live region, such as `role="status"` for non-urgent updates. Use an alert for important, time-sensitive errors only when appropriate. Update status text without unnecessarily moving focus. Use `aria-busy` when a region is being updated and this state is meaningful.                            | **Automated:** Test that status text updates correctly. **Manual:** Use NVDA or another screen reader to confirm updates are announced without requiring the user to move focus.                                                              |

## Additional Accessibility Criteria

| Criterion                            | Where it applies                                                 | Implementation and verification                                                                                                                                                                                                                                                    |
| ------------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **2.4.2 Page Titled (A)**            | All wireframes and React views                                   | Provide a descriptive HTML `<title>` for each page. If React changes views without a full page load, update the document title appropriately. Verify the title in the browser and screen reader.                                                                                   |
| **3.1.1 Language of Page (A)**       | All HTML pages                                                   | Set the document language to `<html lang="en-ZA">` to match the South African English content. Verify that the language attribute is present.                                                                                                                                      |
| **1.4.1 Use of Color (A)**           | Links, validation errors, selected filters and status indicators | Do not use colour as the only means of communicating information. Use descriptive text, underlines, labels or other visual indicators where appropriate. Verify all states manually.                                                                                               |
| **2.4.3 Focus Order (A)**            | Navigation, booking form and React views                         | Ensure keyboard focus follows a logical order that preserves the meaning and operability of the page. Test the complete keyboard sequence.                                                                                                                                         |
| **2.4.6 Headings and Labels (AA)**   | Page headings, form controls and filters                         | Use descriptive headings and labels that communicate each section's purpose. Verify that controls remain understandable when encountered independently in a screen reader.                                                                                                         |
| **2.5.8 Target Size (Minimum) (AA)** | Buttons and other pointer targets                                | WCAG 2.2 adds a 24-by-24 CSS pixel minimum target-size criterion, subject to exceptions. This is not a WCAG 2.1 criterion, so treat it as an additional improvement rather than a WCAG 2.1 AA requirement. A 44-by-44 CSS pixel target is a useful usability goal where practical. |
